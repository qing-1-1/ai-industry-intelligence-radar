### [GPT-6.2 Astra 在 XDOF Ember-0 具身基准成功率翻倍至 41.2%，首通打结与展开 T 恤](https://www.qbitai.com/2026/11/511779.html) ⭐️ 8.0/10

机器人基础设施公司 XDOF 公布的最新 Ember-0 实测显示，OpenAI 的 GPT-6.2 Astra 操控双臂机器人完成 16 项操作任务的综合成功率达 41.2%，较两个月前 GPT-6 Astra 的 19.6%提升 21.6 个百分点、翻了一倍有余，并首次完成此前无 AI 通关的“给绳子打结”和“展开 T 恤”两项任务。成绩公布后，OpenAI Developers 官方账号转发了该消息，OpenAI 联合创始人兼总裁 Greg Brockman 也发文称赞其在机器人技术方面的表现。

rss · 量子位 · 11月21日 06:35

**「关键数据」** 41.2%为 16 项共享操作任务成功率的等权平均，涵盖物体抓取、空间推理、双臂协作、工具使用、精细操作和柔性物体处理等能力。评测以六台 YAM 工作站并行进行，每项任务重复 30 次，单日可完成 480 场实测，并由人工标注子步骤、抓取失误与碰撞。分项提升最明显的是“用夹子夹起面包”：GPT-6 Astra 成功率仅 10%，GPT-6.2 Astra 提升至 90%。速度方面，模型发布期间平均预测延迟从 GPT-6 Astra 的 15 秒降至 10.1 秒。此前 Ember-0 累计进行过 143 次有效的 T 恤展开测试，无一模型成功。此外，新加坡国立大学总统青年教授 Jiafei Duan 称，在其团队的真实机器人对比测试中，GPT-6.2 Astra 一天内冲到 RoboColosseum 的 SO-101 Elo 排名第一。

**「背景」** Ember-0 是 XDOF 推出的面向真实物理环境的机器人评测基准，使用双臂机器人完成 16 项操作任务，每项按 30 次重复协议执行。打结与展开 T 恤对应的核心能力标签包括形变控制、双臂协调、精细操作（Dexterity）和长程规划（Long horizon）：柔性物体形态会随每次接触、抓取和拉扯变化，机器人需从腕部和顶部摄像头画面中持续判断角点、褶皱与整体形态。在无触觉反馈的硬件条件下，大模型每次输出动作块之间存在十余秒到二十余秒的推理延迟，机械臂等待新决策期间无法实时微调。XDOF 在最新推文中表示，Ember-0 基准或不久后便会被模型能力饱和。从行业看，英伟达研究团队测试 GPT-6 Astra 直接充当机器人策略模型、Claude 在机器人模拟环境展现复杂操作能力、Google DeepMind 将 Gemini 多模态理解延伸至机器人控制，通用模型正持续刷新具身智能的能力边界。

在 2026 年 PyTorch 北美大会上，亚马逊云科技（AWS）发布了 TorchNeuron，一个原生 PyTorch 后端。开发者只需将 .to\(&\#x27;cuda&\#x27;\) 改为 .to\(&\#x27;neuron&\#x27;\) 这一处设备配置改动，即可让现有 PyTorch 代码在 AWS Trainium AI 芯片上运行，无需重写或重新验证模型。该后端由 Amazon Annapurna Labs 团队开发。

rss · InfoQ 中文 · 11月22日 10:00

**「关键能力与验证」** TorchNeuron 通过 torch.accelerator 实现 PyTorch 自动设备检测，并原生支持分布式训练与并行 API，包括 DDP、FSDP2、DTensor，同时通过 torch\_neuronx.Stream 和 torch\_neuronx.Event 提供 Torch 流和事件的原生支持。开发者还可借助 Neuron 内核接口（NKI）开发、优化并执行自定义运算符，在模型代码中直接调用对性能至关重要的 NKI 内核以替代标准 ATen 操作，从而获得比自适应即时执行（Adaptive Eager）和 torch.compile 更精细的性能控制。为保障迁移体验，开发团队对 10 万个最受欢迎的模型和 800 多种机器学习架构进行了验证。此外，TorchNeuron 允许企业在训练与推理工作负载之间共享硬件容量，并在非高峰时段将资源从推理重新分配到训练。

**「背景与已披露采用方」** 据亚马逊云科技援引的数据，目前 85% 的人工智能研究人员和开发者使用 PyTorch 编写代码，而此前将代码扩展到新芯片往往意味着重写并重新验证耗时数月打磨的代码。AWS 表示，TorchNeuron 已被多家机构采用，其中包括将该项技术用于语音 AI 推理的 Cartesia，以及探索其在药物靶点识别和药物发现领域应用的利伯脑发育研究所。此次发布紧随谷歌推出 TorchTPU 之后，后者是谷歌为其 TPU 硬件开发的原生 PyTorch 后端。

### [Entire Git Forge：面向编码智能体重构 Git 协作方式](https://www.infoq.cn/article/6swrOq5xUXwVqrREwJwc?utm_source=rss&amp;utm_medium=article) ⭐️ 7.0/10

前 GitHub CEO Thomas Dohmke 推出 Entire，一个专为人类开发者与 AI 编码智能体协作设计的 Git 代码托管平台。Entire 主张传统 PR 模式不适合 AI 智能体高速生成、评审、迭代代码的场景，并以 trails（轨迹）和 continuous memory（持续记忆）为核心重构协作流程。

rss · InfoQ 中文 · 11月21日 10:00

**「产品变化」** Entire 基于全分布式架构构建，代码推送速度最高可达 GitHub 的 89 倍。其核心组件 trails 用于解决 AI 智能体给传统 PR 模型带来的痛点：合并请求时间线已变成只有智能体才会读的审计日志，无法让开发者有把握判断是否可合并。Trail 把关键信息以评估分数形式置顶展示，每次代码推送都会更新分数。Trail 可由缺陷工单或功能需求手动发起，可跨多个代码仓库。每当有新代码推送，运行在云沙箱中的评审智能体会根据代码质量、安全性、slop（低质量代码）以及是否需要人工评审返回分数和理由。每次评估显示最近 5 轮结果和当前结果，评审智能体既可在 Entire 界面配置，也可通过仓库级 JSON 文件配置。开发者可配置仓库级 Gates（门禁）定义合并通过条件，所有评审发现的问题必须在合并前解决或关闭。持续记忆由两个开源工具实现：一个构建 Git 仓库的预计算图谱（含排序后的代码搜索、定义和调用者、类型和路由等），另一个将代码库图谱与之前的智能体会话及 Git 历史结合，创建持久记忆层。Entire 还支持集成 Buildkite、Depot 等 CI 平台。

**「背景」** Entire 现任 CEO、前 GitHub CEO Thomas Dohmke 解释，GitHub 和 GitLab 以异步代码评审与版本控制为中心，改变的是人与人之间的协作方式；而多智能体代码托管平台则以 AI 智能体与人类协同工作的异步编排、版本控制和审计为中心。在 Hacker News 讨论中，Entire 员工 Haimantika 表示，问题从来不在语言或工具本身，而在于推理过程在人与产出物之间被丢弃——提交说明糟糕、文档过时、&\#x27;为什么有这段代码&\#x27;只能靠记得的人解释，智能体放大了这一问题，这正是 Entire 想解决的。Entire 是源码管理赛道的新玩家之一，其他还包括 Zed DeltaDB、Anthropic Scion、East River Source Control、Cursor Origin、Radicle 等。本文为厂商发布内容，相关性能数据未经独立验证。
