## 模型路由与 AI 网关

### [Google Cloud API Gateway 公开预览流式处理与 OpenAI 兼容模型路由](https://www.infoq.cn/article/X2WRCQI4NorJVEvpgX5B?utm_source=rss&amp;utm_medium=article) ⭐️ 7.0/10

谷歌宣布 Google Cloud API Gateway 的流式处理功能进入公开预览阶段，将传统的请求-响应模式扩展至需要实时通信的应用。据谷歌称，这对提供流式模型响应、多步骤代理工作流和交互式会话的 AI 应用尤为重要。该功能使流式端点能够在 API Gateway 背后运行，同时保留现有网关策略和安全控制，解决了此前开发者只能在&quot;放弃流式传输&quot;与&quot;让流式端点绕过网关从而失去身份验证、API 密钥强制执行和可观测性&quot;之间二选一的限制。同一版本还引入了模型路由功能，提供兼容 OpenAI 的单一端点，可根据请求负载中的模型字段将请求路由至 Gemini、Claude 或 OpenAI gpt-oss 模型。

rss · InfoQ 中文 · 11月17日 14:00

**「路由与能力」** 流式传输模式：API Gateway 支持服务器发送事件（SSE）、分块传输编码和 HTTP 响应流式传输、WebSockets 以及 gRPC。流式连接最多可保持打开状态一小时，此后若需继续通信，客户端必须建立新连接。

兼容性与配置：新功能无需更改现有 API 规范，也无需使用特定 API、扩展或注解。谷歌强调，所有现有 API 配置和功能照常运行，包括 API 密钥强制执行、JWT 验证、后端服务账户身份验证、Cloud Logging 和 Cloud Monitoring 集成，以及路径模板和请求路由。

可预测网关主机名：此前网关主机名包含生成的哈希值，只能在网关创建后确定。现在遵循确定性格式 GATEWAY\_ID-PROJECT\_NUMBER.REGION.gateway.dev，开发者可在创建资源前对其进行引用和配置。

模型路由：提供兼容 OpenAI 的单一端点，根据请求负载中的模型字段将请求路由至 Gemini、Claude 或 OpenAI gpt-oss 模型。谷歌表示，模型路由与流式传输结合，意味着客户端可获得熟悉的、基于标准的流式接口，同时仍可集中控制哪些模型可供访问、由谁访问以及遵循何种策略。

AI 场景：借助流式传输，开发者可实时流式传输模型响应、在多步骤任务中更新代理进度、支持工具调用协议和与远程 MCP 服务器的连接，并处理交互式 AI 应用。

**「适用与限制」** 预览状态与启用方式：该功能处于公开预览阶段。预览期间，开发者必须在创建网关时通过指定 --enable-streaming 命令行标志显式启用。

已指出的局限：针对谷歌公告，X 平台用户 emildrops 指出两点局限：一是现有网关无法就地切换；二是延迟衡量的是整个数据流而非首字节到达时间，因此延迟图表可能因非故障原因显得异常。LinkedIn 用户 Ehsan Elahi Zaheer 同样指出，网关请求延迟指标衡量的是数据流持续时间而非&quot;首字节到达时间&quot;，一张延迟图表可能掩盖截然不同的用户体验。

适用范围说明：该产品面向使用 Google Cloud API Gateway 的企业模型服务与网关架构场景，与电信运营商的关联为间接关系。

<a id="item-radar-industry-5"></a>
### [腾讯 Hy4 flash 实测：单任务成本约为 Hy4 二十分之一的 Flash 模型](http://www.geekpark.net/news/374083) ⭐️ 8.0/10

极客公园发布了对腾讯新推出的 Flash 模型 Hy4 flash 的实测评测。该模型总参数量 224B（含 64B Engram 参数），实际激活参数仅 12B，定位为高吞吐、低成本、面向 Agent 场景的性价比模型，官方称单任务成本仅为 Hy4 的二十分之一。评测方在获得内测资格后，将其与 DeepSeek-V4.1-Flash（1017 版本）及正式版 Hy4 进行了四轮对照测试，涵盖办公决策、读图决策、编程修复和论文转 PPT。

rss · 极客公园 · 11月17日 07:12

**「关键数据与产品特性」** 架构与能力：总参数 224B（含 64B Engram 参数），预训练阶段加入混合注意力、LatentMoE、Engram 等架构特性，实际激活参数 12B；KV cache 大小为 Hy3 的 1/24、Hy4 的 1/6；支持多模态和 1M 上下文长度。后训练阶段通过自蒸馏 Hy4 获得综合智能水平，并通过强化学习使端到端任务输出长度降低 50%。推理效率上结合 megakernel、4bit 量化、DFly 等手段优化，解码速度可超过 150 tps。

定价：每百万 Token 输入 0.5 元、输出 2 元，命中缓存时仅需 0.02 元，价格较 Hy4 大幅降低。

成本对比：官方称整体单任务成本仅为 Hy4 的二十分之一。

四轮实测结果：办公决策中，Hy4 flash 用时 1 分 14 秒，比 DeepSeek-V4.1-Flash（4 分 8 秒）少用 2 分 54 秒，核心判断一致；读图决策中，Hy4 flash 用时 2 分 46 秒，识别出「6 家意向客户被标为可计收入、实际只有 1 家确认付费」的冲突，而更快的 DeepSeek-V4.1-Flash（1 分 25 秒）出现两处明确误判；编程修复中，Hy4 flash 用时 2 分 5 秒找到并修好全部 4 个问题并新增 5 个测试，正式版 Hy4 用时 3 分 49 秒、新增 8 个测试；论文转 PPT 中，Hy4 flash 用时 9 分 5 秒生成 21 页 PPT，正式版 Hy4 用时 15 分 47 秒生成 18 页 PPT，后者页面更适合直接讲解。

**「背景」** 评测指出，2026 年 Agent 流行后，行业关注点从模型能力领先转向用得起、等得起。OpenRouter 披露，2026 年 2 月 6 日平台上 Agent 的 Token 用量首次超过人类直接调用，到 9 月底已约为后者的七倍。密歇根大学与斯坦福大学一项覆盖 8 款模型、500 个真实代码问题的研究发现，Agent 每次尝试处理一个问题平均累计消耗约 417 万 Token，模型调用费约 1.86 美元。OpenRouter 与 a16z 对超过 100 万亿 Token 使用数据的研究发现，Gemini 2.0 Flash、DeepSeek V3 0324 等兼顾能力与低成本的模型已获得与部分高价领先模型相近的用量；2026 年 11 月 14 日，DeepSeek、智谱的 Flash 模型同时进入 OpenRouter 单日 Token 用量前十。腾讯混元官方 Blog 推荐在深度搜索、文档处理、PPT 生成、简单前端展示、computer use 等日常任务中使用 Hy4 flash，在长程软件工程等复杂任务中使用智能上限更高的 Hy4。评测同时说明，包括 Hy4 flash 在内的 Flash 模型在准确率上相比当下 SOTA 模型仍有距离。

DigitalOcean 推出 DigitalOcean Managed Agents 公开预览版，为 AI 智能体提供一层托管的云端基础设施。该产品整合 Harness Runtime（基于 microVM 的持久化隔离运行时）与 Action Gateway（受管控的工具访问接口），为 Claude Code、Codex CLI、OpenCode、Hermes 及基于 LangGraph 构建的自定义智能体提供隔离运行环境、工具访问与无服务器 AI 推理能力。

rss · InfoQ 中文 · 11月16日 16:42

**「产品变化」** Harness Runtime 基于轻量级 microVM 构建，为智能体提供持久化、隔离的计算环境。它可跨会话持久化保存对话历史与工作状态，会话支持暂停、恢复或分叉（fork）；当会话空闲（无进行中的 LLM 调用或工具调用）时自动暂停智能体。每个会话运行在安全加固的计算与存储资源上，允许开发者连接内部服务而无需暴露到公网，并可跨代码仓库和任务并行启动，支持分而治之、协作及 map/reduce 工作流。

Action Gateway 是智能体访问外部工具与服务的统一接口，通过单一 MCP 端点对外提供，目前已有超过 16000 种工具，涵盖 Web Search、Web Fetch、Browser Automation、DigitalOcean 基础设施管理 API，以及面向 GitHub、HubSpot、Stripe 等平台的连接器。该网关实现集中式权限管理（界定每个智能体可用的工具与操作）、对敏感操作强制人工审批，并提供速率限制、重试、退避和超时机制以支持多智能体访问外部系统。

**「背景」** DigitalOcean 指出，智能体工作流与传统云端应用存在本质差异：若在常规虚拟机上运行智能体，开发者需自行维护上下文、持久化制品、协调并行工作、为工具提供安全加固的访问，并维持闲置虚拟机容量以确保快速启动。Managed Agents 旨在通过 Harness Runtime 与 Action Gateway 应对这些挑战，将执行、持久化、工具访问与基础设施交由 DigitalOcean 管理。

该产品推出时间与 Docker Cloud Sandboxes 大致同期，二者在沙箱与运行时层面存在显著重叠，均提供 microVM 隔离与持久化能力。区别在于：Docker Cloud Sandboxes 更聚焦开发者工作流，尤其是沙箱在本地与云端算力之间迁移的能力；DigitalOcean Managed Agents 则更聚焦生产环境基础设施，并提供更丰富的编排与工具支持。

### [Docker 将 Sandbox Kit v3 规范捐赠给 CNCF：把 AI 智能体权限打包为 OCI 镜像](https://www.infoq.cn/article/yV89L6iMCqSLDHeSoLxo?utm_source=rss&amp;utm_medium=article) ⭐️ 7.0/10

Docker 宣布将 Sandbox Kit 规范捐赠给 CNCF，采用 Apache 2.0 许可，并升级至 v3 版本。该规范把一个 AI 智能体、它所使用的工具，以及一份经过类型化声明的、所申请的主机（hosts）、凭证（credentials）和卷（volumes）清单，统一打包为一个普通的 OCI 镜像，使智能体的权限具备与智能体本身相同的可移植性。

rss · InfoQ 中文 · 11月16日 16:22

**「产品变化」** 在 v3 版本中，Kit 不再是一种独立的构件类型：它没有自定义的媒体类型，也没有附属的边车文件，其清单中只包含一项声明 vnd.docker.sandbox.kit.descriptor。因此 Kit 可以用 docker buildx build 构建、用 docker pull 拉取，并能被扫描、签名或在 FROM 指令中引用；固定摘要即等于把内容与权限一起固定下来。

各项声明都是具有类型化、版本化的能力，例如 com.docker.sandbox/network-policy@2 和 com.docker.sandbox/credential@1。在规范的 GitHub CLI 示例中，Kit 允许访问 api.github.com，但拒绝对 /repos/\*\* 执行 DELETE 操作，因为&quot;拒绝&quot;的优先级高于&quot;允许&quot;。凭据可由代理托管：符合规范的运行时会把真实令牌注入到发往指定域名的请求中，而沙箱内部只存在一个哨兵值。

启动时，会将一个提供根文件系统的工作负载 Kit 与任意数量的混入叠加层组合，混入的排序依据 provides/requires 依赖图而非命令行标志顺序；若某个 requires 未满足或两个 Kit 提供了同一名称，解析就会失败。相互重叠的声明会进行协调：网络规则取并集，不兼容的规则则被视为错误。每份描述符还可归约为规范化的授权集合，对更新进行门控的运行时可记录该集合并阻止任何扩大其范围的新版本，包括移除了 deny 规则的版本。规范随附两套一致性测试套件，分别针对 Kit 构件和运行时。

**「背景与适用范围」** 像 Claude Code 和 Codex 这样的智能体会代表用户安装包、调用 API 并使用凭据，而让它们发挥作用的授权（如绑定挂载、范围过宽的令牌、被放开的防火墙规则）通常散落在 shell 历史记录、各类控制台看板和人的记忆中，而非存放在可供审阅的构件里。Docker 认为这正是 OCI 当初要防止的碎片化问题，否则每个运行时厂商都可能各自发明一套方案。

Kit 只是&quot;申请&quot;权限，最终由主机裁定：若缺乏符合规范的运行时，该注解即无效；若某项必需的申请无法满足，启动会被拒绝。Docker Sandboxes（在拥有独立内核的 microVM 中运行智能体）是第一个符合规范的运行时。Docker 表示将与 AWS、Box、Datadog、Dynatrace、JFrog、NanoClaw、OpenClaw、Palo Alto Networks 及 Snyk 等公司携手打造 Kits，并将此举与当年捐赠镜像格式和 runc、最终催生 OCI 的举措相类比。CNCF CTO Chris Aniszczyk 对此表示欢迎。

不过，材料并未说明该规范是否已被纳入 CNCF 的某个孵化项目，也未提及它将进入哪一个成熟度等级。工程师可访问 docker/sandbox-kit-spec 仓库，通过 sbx CLI 测试示例（如 sbx run ./hello --kit ./gh）。现有镜像仓库、扫描工具和签名工具无需改动即可处理 Kits，但描述符语法及每项能力的具体语义都是全新的。需注意的是，权限执行完全取决于运行时，由于 Docker Sandboxes 目前是唯一符合规范的实现，跨运行时的可移植性尚未得到验证。在治理结构变更前，Docker 将继续维护该规范。
