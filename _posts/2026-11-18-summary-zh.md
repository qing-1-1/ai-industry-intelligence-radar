### [LiteLLM 发布 v1.110.0：路由回退、多供应商流式与 SpendLogs 记账变更](https://github.com/BerriAI/litellm/releases/tag/v1.110.0) ⭐️ 7.0/10

BerriAI 于 2026 年 11 月 18 日发布开源 LLM 网关/路由项目 LiteLLM 的 v1.110.0 版本。该版本包含路由回退行为修复、多供应商流式支持、代理安全加固，以及将 SpendLogs 账本设为默认记账路径等变更。完整变更列表见 GitHub Release（v1.109.1...v1.110.0）。

github · litellm-release\[bot\] · 11月18日 01:36

**「路由与能力」** 路由与回退：修复了回退在同一 key、无 api\_base 的部署间跳转时保留加密推理（encrypted reasoning）的问题；新增 Rust 路由核心（以宿主为唯一边界），并删除了 Python 路由核心；修复了注册表锁与请求字段校验问题。

多供应商流式与透传：在 /v1/messages 上对 Azure OpenAI 主机上的 azure\_ai 进行原生流式；对每个 OpenAI websocket 透传帧检查模型；在流式 chat completion 分块上保留供应商字段；在每个桥接流式事件上序列化 sequence\_number。

记账与成本：将 SpendLogs 账本设为默认记账路径；流式 /v1/responses 的消费行按客户端收到的加密 resp\_ id 保存；在未安装 prometheus\_client 时保持消费提交可用；恢复用户聚合路由上的每用户消费拆分；补充多项成本映射与 token 计数（含 Gemini Flex 长 prompt 价格、gemini omni 1.2 flash 定价与限额、grok-4-1/grok-4.3/DeepSeek V4.1 工具请求计费口径、Bedrock Web Search 与 Mantle 行定价）。

网关与其他能力：新增将 HTTP 请求转发到 Python 代理的网关能力；新增可移植的 Agent Skills Hub API、版本历史、提交与管理员审核、可选手动安全扫描、下载量与历史展示；模型弃用前邮件通知受影响所有者；新增 supports\_continuation 能力标志（Gemini 长解码续写）与 hosted\_vllm 的 stop\_reason/token\_ids 保留。

安全与可观测性：将 /update/sso\_settings 改为真正的 PATCH 并仅发送变更的 SSO 字段；修复在无 api\_key 部署上误用 OPENAI\_ADMIN\_KEY 作为 bearer token；修复 GitHub Copilot 直接发送 token 而非交换；Prometheus 在代理失败时保留部署归属；修复每请求 Redis 批处理作用域泄漏。

**「适用与限制」** 该版本面向使用 LiteLLM 作为模型网关/路由的自建部署方，Docker 镜像 ghcr.io/berriai/litellm:v1.110.0 提供 cosign 签名校验。来源为社区开源项目发布说明，未涉及运营商部署、招标或容量数据；部分变更带感叹号标记（breaking），升级前需对照完整变更列表评估兼容性。

<a id="item-radar-router-3"></a>
### [Google Cloud API Gateway 公开预览流式处理与模型路由](https://www.infoq.cn/article/X2WRCQI4NorJVEvpgX5B?utm_source=rss&amp;utm_medium=article) ⭐️ 7.0/10

谷歌宣布公开预览 Google Cloud API Gateway 的流式处理功能，将传统的请求-响应模型扩展至需要实时通信的应用。据谷歌称，这对提供流式模型响应、多步骤代理工作流和交互式会话的 AI 应用尤为重要。该功能使流式端点能够在 API Gateway 背后运行，同时保留现有网关策略和安全控制。同一版本还引入了模型路由功能，提供兼容 OpenAI 的单一端点，可根据请求负载中的模型字段将请求路由至 Gemini、Claude 或 OpenAI gpt-oss 模型。

rss · InfoQ 中文 · 11月17日 14:00

**「路由与能力」** 流式传输支持：API Gateway 支持多种流式传输模式，包括服务器发送事件（SSE）、分块传输编码和 HTTP 响应流式传输、WebSockets 以及 gRPC。流式连接最多可保持打开状态一小时，此后若需继续通信，客户端必须建立新连接。新功能无需更改现有 API 规范，也无需使用特定 API、扩展或注解；现有 API 配置和功能照常运行，包括 API 密钥强制执行、JWT 验证、后端服务账户身份验证、Cloud Logging 和 Cloud Monitoring 集成，以及路径模板和请求路由。

模型路由：提供一个兼容 OpenAI 的单一端点，根据请求负载中的模型字段将请求路由至 Gemini、Claude 或 OpenAI gpt-oss 模型。模型路由与流式传输结合后，客户端可获得基于标准的流式接口，同时可集中控制哪些模型可供访问、由谁访问以及遵循何种策略。

可预测网关主机名：此前网关主机名包含生成的哈希值，只能在网关创建后确定；现在遵循确定性格式 GATEWAY\_ID-PROJECT\_NUMBER.REGION.gateway.dev，使开发者能在创建资源前引用和配置。

预览期启用方式：开发者必须在创建网关时通过 --enable-streaming 命令行标志显式启用该功能。

**「适用与限制」** 外部用户指出的局限：X 平台用户 emildrops 指出，现有网关无法就地切换；且延迟衡量的是整个数据流而非首字节到达时间，延迟图表可能因非故障原因显得异常。LinkedIn 用户 Ehsan Elahi Zaheer 同样指出，网关请求延迟指标衡量数据流持续时间而非首字节到达时间，一张延迟图表可能掩盖截然不同的用户体验。本文为 InfoQ 翻译的二手报道，来源未提供更多细节。
